# ADR-0004: Версии вычислителей и отдельные семейства метрик

Status: Accepted
Date: 2026-10-25

## Context

Владелец указал использовать официальный difficulty/performance calculation osu!
как основу для выбора сохраняемых метрик, учитывать обновления формул и появление
новых атрибутов. Собственные метрики появятся позднее. Текущий `basic-raw/1`
содержит простые raw измерения и не реализует официальный difficulty/pp.

Одной версии нашего алгоритма недостаточно для идентификации внешнего engine,
его binding и upstream revision. Difficulty и performance также имеют разные
входы: performance зависит от score/scenario. Общая постоянно расширяемая таблица
всех показателей смешала бы разные контракты и сроки их развития.

## Decision

1. Официальный код и релизы — исходная точка семантики; сторонний port подключается
   через адаптер с проверенной поддерживаемой ревизией. `master`, версия сайта
   и версия порта не объявляются взаимозаменяемыми.
2. Разделить `basic_raw`, `osu_difficulty`, `osu_performance` и будущие собственные
   показатели. Для каждого нового семейства вводить типизированный snapshot/table
   вместе с первым работающим сценарием. Performance ссылается на difficulty
   snapshot и сохраняет полный контекст score/scenario.
3. Идентичность результата включает точные байты входа, provider/build и underlying
   engine, известную upstream revision, adapter/schema versions, ruleset/mods/settings,
   clock rate и применимую совместимость. Неизвестная upstream revision явно nullable.
   Обновление вычислителя создаёт новую запись; исторические значения сохраняются.
4. Новые scalar fields вводятся миграциями; отсутствие значения не подменяется нулём.
   Изменение смысла/единиц получает отдельный metric identifier. Доступность полей
   и определения фиксируются версионируемым контрактом, а не произвольным output JSON.
5. API snapshots имеют собственное происхождение. Дата получения не является engine
   version; API-значению нельзя назначить ревизию локальной библиотеки без основания.
6. Сейчас фиксируется архитектурное направление. Runtime/migration первого внешнего
   вычислителя обязаны реализовать этот контракт до сохранения его результатов;
   пустые таблицы, фиктивные provider versions и зависимости заранее не добавляются.

[ADR-0003](0003-transient-inputs-compact-results.md) сохраняет силу: PostgreSQL,
типизированные метрики, малый configuration JSONB и временные исходники.
Полный контракт эволюции и проверенные источники:
[metric-evolution](../architecture/metric-evolution.md).

## Alternatives

- Только общий `algorithm_version`: не различает wrapper, upstream engine и наш adapter.
- Полный output в JSONB или EAV `metric_name/value`: упрощает произвольное добавление
  ключей, но не решает семантику версий и усложняет типизацию/поиск устойчивых метрик.
- Автоматически обновлять и пересчитывать старые результаты: скрывает изменение
  модели и требует исходников, которые по выбранной политике уже освобождены.
- Немедленно добавить все предполагаемые поля: закрепляет непроверенный контракт
  библиотеки до выбора её ревизии и реального сценария.

## Consequences

Подключение engine требует миграции и проверки соответствия полей; сравнение
результатов учитывает версии. При этом новые метрики не требуют смены PostgreSQL
или хранения карты целиком. Существующие 22 поля и API остаются текущим raw baseline.

Ближайший запланированный срез — osu! API metadata/identity, затем M2. В M3 первым
идёт выбранный difficulty engine, а собственные метрики развиваются после него.

## Revisit conditions

Первый рабочий adapter/официальный API snapshot уточняет конкретное DDL. Потребность
в произвольных пользовательских метриках или измеренная стоимость миграций могут
потребовать другого хранения; само обновление upstream этого не доказывает.
