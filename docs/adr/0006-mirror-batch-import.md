# ADR-0006: Пакетный импорт и зеркала как отдельные источники

Status: Accepted
Date: 2026-10-25
Supersedes: decision 6 of ADR-0005

## Context

Пользователь предложил пакетное получение карт через зеркала, указал Hinamizawa
и необходимость дополнительного источника при official API 429. Это конкретный
сценарий для M2: независимые загрузки/анализы, частичные результаты и retry.

В просмотренной документации batch endpoint разрешает metadata, raw `.osu`
получается по одной difficulty. Предположение о скачивании произвольного списка
файлов одним batch response не подтверждено. Не вся mirror metadata независима
от официального upstream, поэтому fallback не является гарантией доступности.

## Decision

1. Первым прикладным сценарием M2 сделать наш batch API: durable items, очередь,
   worker и per-item status; initial cap 100 difficulty IDs. Upstream batch
   применяется для metadata, raw файлы скачиваются с ограниченной конкуренцией.
2. Допустить mirror как явно выбранный download/metadata provider. Пункт 6 ADR-0005
   заменяется этим решением: официальный неподходящий grant не используется,
   а зеркало интегрируется по собственному контракту. M1a runtime не меняется.
3. Сохранить отдельные provider budgets/cooldowns. Official 429 не сбрасывается;
   mirror/cache можно использовать параллельно по его условиям. Relay pressure
   обрабатывается ожиданием/retry, а не бесконечной ротацией источников.
4. Разделить download provenance, mirror claims и официальную checksum-сверку.
   Mirror данные не попадают в `osu_beatmap_matches` как официальный результат.
   Перед первым сохранением добавить необходимый DTO/DDL происхождения.
5. Использовать raw `.osu` как начальную стратегию, ограничивать размер/число
   загрузок, хранить bytes только на период обработки/retry. Metadata/результаты
   остаются табличными. Новая редакция определяется hashes, а не только ID.
6. Не импортировать внешний PP/enrichment output без контракта ADR-0004.
   При недоступной официальной сверке допустим явно обозначенный mirror input;
   отсутствие подтверждения не скрывается.

Полный проект сценария и проверенные источники:
[batch-import](../architecture/batch-import.md).

## Alternatives

- Только официальный metadata API: не решает получение raw input и не использует
  предложенный пользователем альтернативный источник.
- Скачивать `.osz`/pack для каждого набора IDs: тратит место/трафик на ненужные
  ресурсы и не соответствует начальной задаче анализа отдельных difficulties.
- Перенаправлять текущий OAuth client на mirror: смешивает доверие, секреты и
  формат источника с официальной сверкой.
- Запускать весь batch в одном HTTP-запросе: усложняет восстановление и частичный успех.

## Consequences

У M2 появляется проверяемый пользовательский сценарий. Понадобятся provenance,
job delivery/retry и общий provider budget; одного списка URLs недостаточно.
Hinamizawa — проверенный по документации кандидат, живой download ещё не выполнен.

Implementation note, 2026-10-25: первый срез реализовал adapter, single-file HTTP
import и versioned provenance. Проверен один живой raw file; durable batch/worker
по-прежнему впереди. Контракт: [mirror-import](../architecture/mirror-import.md).

## Revisit conditions

Рабочий adapter/OpenAPI contract, изменившиеся условия provider, измеренная
производительность raw загрузок, необходимость packs или конкретных revisions.
