# ADR-0003: Временные исходники и компактные табличные результаты

Status: Accepted
Date: 2026-10-25

## Context

Reader уже извлекает metadata, timing points и hit objects. CLI summary
показывает только metadata и counts, но анализу нужны сами объекты. Владелец
уточнил жизненный цикл: объекты доступны во время вычислений; после анализа
нужны только идентичность карты и результаты. Постоянное хранилище исходников,
строка на каждый объект или JSON-копия разобранной карты не соответствуют
этому требованию.

[ADR-0002](0002-postgresql-async.md) сохраняет силу: PostgreSQL остаётся
единственной БД, транзакции явные, схема меняется Alembic. Настоящее решение
уточняет выбранную там возможность JSONB и заменяет предварительное направление
модели из architecture/database: отдельные BeatmapSet/Beatmap с уникальными
внешними IDs сейчас не вводятся. ID в загруженном файле ещё не подтверждён
проверкой на сайте.

## Decision

1. Reader и анализ работают с объектами и timing points в памяти CPU-процесса.
   Из него возвращаются компактные metadata/settings и скалярные измерения.
   HTTP upload читается ограниченным потоком в память; постоянный исходник и
   временный файл на диске этот сценарий не создаёт.
2. `beatmap_inputs` хранит fingerprint точного входа: SHA-256, MD5, размер,
   format/ruleset, ограниченные title/artist/creator/difficulty name, claimed
   IDs и версию reader первоначальной metadata. SHA-256 — уникальный `BYTEA`
   длиной 32 байта. MD5 — неуникальный `BYTEA` длиной 16 байт с обычным индексом;
   он пригоден как совместимый lookup-атрибут, но не служит ключом идентичности.
3. `claimed_beatmap_id` и `claimed_beatmap_set_id` nullable, неуникальны и
   не являются доверенными внешними ключами. Контракт явно возвращает
   `identity_status="unverified"`. Unsubmitted карты не получают выдуманный
   ID. Проверка через API и авторитетные связи с сайтом остаются отдельной задачей.
4. `analysis_results` связан с входом через FK `ON DELETE RESTRICT`.
   Difficulty settings, stack leniency и все 22 признака `basic-raw/1`
   сохраняются отдельными числовыми столбцами. Сырые файлы, медиа, массивы
   hit objects/timing points и JSON feature vectors не сохраняются.
5. JSONB допускается только для объекта `configuration` с ограничением
   `octet_length(configuration::text) <= 4096`. Текущая конфигурация фиксирует
   ruleset 0, отсутствие mods, raw coordinates и parser limits. Application
   считает SHA-256 канонического JSON. Уникален ключ
   `(input_id, algorithm_version, parser_version, configuration_sha256)`;
   версия parser metadata входа при этом остаётся прежней.
6. Вход и результат сохраняются одной явной транзакцией после вычислений.
   Конкурентные повторы разрешаются `INSERT ... ON CONFLICT DO NOTHING RETURNING`
   и отдельным `SELECT` после конфликта при `READ COMMITTED`. Существующие
   строки не перезаписываются. Уникальность относится к записям результата,
   а не к количеству запусков вычислений.

Полный контракт таблиц, hash-конфигурации и ограничений:
[database](../architecture/database.md).

## Alternatives

- Постоянно хранить `.osu` в object storage или БД: позволяет переанализировать
  прежний файл без повторного получения, но нарушает выбранный владельцем
  жизненный цикл и требует отдельной политики хранения.
- Нормализовать каждый объект/timing point в строки: возвращает сохранение
  исходной карты в другую форму и увеличивает число строк пропорционально
  числу объектов, хотя поиск по ним текущему сценарию не нужен.
- Сохранять `ParsedBeatmap` или результат целиком как JSONB/NoSQL document:
  переносит исходные массивы в хранилище и скрывает устойчивые признаки от
  типизированной схемы и обычных ограничений.
- Дедуплицировать по BeatmapID или MD5: объединяет неподтверждённые claims,
  разные версии файла или потенциальные совпадения MD5.

## Consequences

Количество столбцов не зависит от числа объектов; новый устойчивый признак
появляется вместе с миграцией и версией алгоритма. PostgreSQL обеспечивает FK,
unique/check constraints и атомарное сохранение. Конкретная экономия места
не заявляется до измерения строк и индексов на репрезентативных данных.

Воспроизведение результата требует прежних байтов, кода и параметров. SHA-256
подтверждает точность повторно полученного входа, но не восстанавливает его.
После обработки новый анализ требует повторно получить `.osu`; один и тот же
ID сайта не гарантирует доступность исторической версии. Изменение любого
байта, включая игнорируемый текст медиа-ссылки, создаёт новый fingerprint.

Metadata первого импорта сохраняется без обновлений. Новая версия reader
может создать новый результат для того же входа; исправление прежней metadata
потребует отдельного явно выбранного сценария. Триггеров, запрещающих
административный SQL `UPDATE`, текущая схема не содержит.

Локальный `extract-osz` остаётся инструментом разработки: он сохраняет
выбранный оператором корпус и не удаляет пользовательские архивы. Его output
не является production source storage. Обработка в памяти также не обещает
криптографическое стирание RAM. Долговечные очередь/worker и retry пока не
реализованы; перед их добавлением нужно определить владение staging-входом
и момент его удаления.

## Revisit conditions

Явное требование повторного анализа без нового получения `.osu`, подтверждение
идентичности через внешний API, измеренная необходимость поиска по сегментам,
расширение ruleset/mods или переход к надёжным фоновым заданиям. Постоянное
хранение исходников потребует нового решения и изменения текущего требования
владельца; само появление новых признаков такого хранения не требует.
