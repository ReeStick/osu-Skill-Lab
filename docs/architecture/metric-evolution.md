# Эволюция difficulty/pp-метрик

Status: Accepted design; difficulty/pp integration not implemented
Date: 2026-10-25

## Отправная точка

Владелец задал официальный difficulty/performance calculation osu! как первую
основу для выбора метрик. Собственные показатели добавляются позднее, с отдельными
математическими определениями. Текущие 22 `basic-raw/1` — технический baseline,
а не реализация официального difficulty/pp и не окончательный набор признаков.

При выборе показателя проверяются официальный код, объявленный релиз и фактически
поддерживаемая ревизия вычислителя. Календарный интервал обновлений не является
ключом версии. `master` osu!, развёрнутая версия сайта и сторонний port могут
отличаться; совпадение названия метрики ещё не доказывает совпадение расчёта.

## Разделение семейств

| Семейство | Вход и смысл | Хранение |
| --- | --- | --- |
| `basic_raw` | Наблюдаемые параметры и простые измерения исходной карты | Существующая `analysis_results` |
| `osu_difficulty` | Карта, ruleset, mods/settings, clock rate и режим совместимости вычислителя | Будущая типизированная таблица семейства |
| `osu_performance` | Difficulty snapshot и конкретный score или полностью заданный сценарий игры | Будущая отдельная таблица со ссылкой на difficulty snapshot |
| `skill_lab` | Собственные определения признаков и затем интерпретации skill profile | Добавляется при наличии формул и проверки гипотез |

Difficulty aim/speed и performance aim/speed — разные величины и разные поля.
Общие имена нельзя объединять только потому, что они похожи. Значение pp всегда
связано со score/scenario; например, SS projection требует явно заданных условий,
а не неявного универсального «pp карты». Контекст включает применимые hit results,
combo, misses, slider judgements и stable/lazer/classic semantics вычислителя.

Определяемые tags — отдельный categorical contract, не универсальная feature
таблица: definitions/bundles и assignments со ссылками на versioned measurements.
Будущие timing/slider geometry/ML providers, мягкий budget 30 s и GPU capability
описаны в [tag-pipeline](tag-pipeline.md), решение:
[ADR-0008](../adr/0008-extensible-tags-and-compute-budget.md).

## Происхождение и идентичность расчёта

До сохранения первого внешнего расчёта его контракт и миграция должны добавить:

- имя provider и точную версию пакета/сборки вычислителя; для binding — также
  идентичность underlying engine, а не только Python wrapper;
- upstream commit/release, которому соответствует порт, если он известен;
  неизвестная ревизия остаётся явно неизвестной;
- версию нашего adapter и контракта выходных полей;
- SHA-256 исходных байтов и versioned параметры декодирования;
- ruleset, нормализованные mods с настройками, clock rate и применимые режимы
  совместимости; для performance — полный нормализованный score/scenario;
- время вычисления, которое не подменяет версию математической модели.

Эти значения входят в идентичность/canonical hash расчёта и дедупликацию.
Обновление provider, engine или adapter создаёт отдельный результат, сохраняя
старый. Одинаковые результаты для разных ревизий не дают права объединить версии.
Текущий ключ `basic-raw/1` менять ради документа не требуется: внешнего provider
в runtime пока нет. Его поля нельзя молча использовать для pp без новой миграции
и контракта происхождения.

Результаты API сайта — отдельный источник. Если API не сообщает точную ревизию
вычислителя, snapshot хранит источник, время получения, идентичность карты и
параметры запроса с неизвестной engine revision. Ему не назначается версия
локально установленной библиотеки и не обещается побитовая воспроизводимость.
Изменение выбранных API-атрибутов обнаруживается по hash их нормализованного
snapshot и параметров запроса; при неизвестной engine revision оно всё равно
создаёт отдельное наблюдение. Совпадение hash значений не доказывает одинаковую
upstream revision. Хранение таких наблюдений определяется сценарием интеграции.

## Изменение состава полей

Семейства развиваются отдельно, без обязательного расширения одной общей таблицы
всеми будущими метриками. При первом работающем сценарии семейство получает
типизированную таблицу и schema contract. PostgreSQL остаётся основной БД;
исходные объекты и произвольный JSON output вычислителя не сохраняются.
Существующее ограничение JSONB для малой конфигурации сохраняет силу.

Для каждого выбранного показателя в коде/документации фиксируются имя с namespace,
тип, единица или безразмерность, определение/ссылка на upstream, версия определения,
допустимые значения и доступность для поддерживаемых engine revisions.

- Новый показатель — явное поле, миграция и новая версия контракта. Старые строки
  получают `NULL`, если показатель не вычислялся; 0 не означает отсутствие данных.
- Новая формула с прежним смыслом — новая версия engine/определения и новый snapshot.
- Новая единица или иной смысл — отдельное поле/идентификатор; историческое значение
  не переименовывается в несовместимую величину.
- Удалённое upstream поле остаётся доступным в старых результатах. Новая версия
  объявляет отсутствие поддержки; API сериализует результат по его контракту.
- Новый неизвестный атрибут provider не сохраняется автоматически. Проверка состава
  полей должна выявить изменение, после чего выбираются смысл, тип и миграция.

Таким образом, расширяемость обеспечивают версии, адаптеры и миграции; таблица
`metric_name/value` на каждую величину и document database сейчас не вводятся.

## Обновление вычислителя

Перед обновлением сопоставить changelog/официальный код, ревизию порта и доступные
поля; выбрать точную сборку. Затем проверить synthetic fixtures, известные сценарии
mods/score, старые snapshots и сравнение старой/новой версии на одном входе.
Численные отклонения фиксируются с допуском и объяснением; нельзя обновлять expected
values только ради прохождения тестов. В пользовательских исследованиях сравниваются
совместимые версии; применение нового engine ко всему корпусу — отдельное действие.

Если нужен показатель, который provider не экспортирует, сначала проверяется
возможность другого адаптера/расширения. Он не восстанавливается неявной эвристикой
и не объявляется официальным. Собственная реализация появится с отдельным определением.

После удаления `.osu` новый расчёт всё равно требует повторного получения точных
байтов. API lookup по ID не гарантирует прежнюю редакцию; SHA-256 проверяется заново.

## Связь с интеграцией osu! API

Срез M1a реализовал metadata/identity через osu! API v2: OAuth-конфигурация,
lookup, checksum verification, раздельное хранение file claims и API metadata,
кэширование и ограничения запросов. Подтверждение через совместимый checksum
не превращает MD5 в криптографическое доказательство: SHA-256 остаётся локальной
идентичностью точных байтов.

Документация API содержит `POST /beatmaps/{beatmap}/attributes` для difficulty
с ruleset/mods. Выбор использования этого endpoint и локального engine делается
отдельно. API не заменяет наличие hit objects для наших вычислений. Способ получения
`.osu` и его доступность проверяются отдельно; массовая загрузка архивов не предполагается.

Очередь/retry/staging — M2. Подключение difficulty engine и сопоставление метрик —
первый срез M3, затем собственные признаки. Сейчас добавлены OAuth-адаптер,
явная checksum-сверка и metadata cache, но не quantitative attributes или новый
difficulty/pp engine. Контракт: [osu-api](osu-api.md). Живая авторизованная
checksum-сверка и переиспользование metadata проверены на одной карте.

## Проверенные источники, 2026-10-25

- [OsuDifficultyAttributes](https://github.com/ppy/osu/blob/master/osu.Game.Rulesets.Osu/Difficulty/OsuDifficultyAttributes.cs):
  в просмотренном `master` есть aim/speed/flashlight/reading и вспомогательные
  атрибуты; это наблюдение исходного кода, а не доказательство версии сайта.
- [OsuPerformanceAttributes](https://github.com/ppy/osu/blob/master/osu.Game.Rulesets.Osu/Difficulty/OsuPerformanceAttributes.cs)
  и [OsuPerformanceCalculator](https://github.com/ppy/osu/blob/master/osu.Game.Rulesets.Osu/Difficulty/OsuPerformanceCalculator.cs):
  performance-компоненты и зависимость расчёта от score statistics.
- [rosu-pp README](https://github.com/MaxOhn/rosu-pp#readme) описывает происхождение порта;
  [rosu-pp-py Cargo.toml](https://github.com/MaxOhn/rosu-pp-py/blob/main/Cargo.toml)
  отделяет wrapper от underlying engine. Это кандидат, не уже выбранная зависимость.
- [osu! API v2](https://osu.ppy.sh/docs/): lookup, beatmap metadata, difficulty
  attributes, OAuth и правила использования. Metadata adapter реализован и
  проверен локально и живой авторизованной checksum-сверкой одной карты.
